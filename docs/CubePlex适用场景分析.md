# CubePlex 适合做什么应用

> 依据：CubePlex 官方 Core Concepts 文档、部署文档、README，以及前两轮对其源码的实读。
> 结论分档：**【文档】**= 官方文档明确写；**【实测】**= 读其源码确认；**【判断】**= 我的推论。

---

## 1. 一句话定位

**CubePlex 是「给一个团队配一个长期在线的 AI 同事」，不是「业务系统的开发平台」。**

它擅长：**让 AI 在真实执行环境里干活，并把成果沉淀成团队资产。**
它不做：表单、审批流、台账、业务状态机、数据权限分级。

这个区分是判断「适合做什么」的唯一有效标准。下面展开。

---

## 2. 它的能力清单（决定适合什么）

### 2.1 具备的（官方文档明确）

| 能力 | 说明 | 来源 |
|---|---|---|
| **多入口访问** | Web + Slack/Discord/Teams/飞书/钉钉/企业微信，同一个 Agent | 【文档】README |
| **持久化沙箱** | 每个工作区独立运行时；文件、依赖、工作树重启后保留 | 【文档】 |
| **代码执行** | Agent 可在 OpenSandbox 沙箱内跑代码 | 【文档】Core Concepts |
| **产物（Artifacts）** | 可版本化、可预览、可下载：文件、网站、图片、数据表 | 【文档】 |
| **三层记忆** | Personal / Workspace / Organization | 【文档】 |
| **MCP 工具** | 接外部 API：数据库、SaaS、内部服务；支持 OAuth / 静态凭据 | 【文档】 |
| **技能（Skills）** | 内置 / 组织上传 / 远程注册表（skills.sh） | 【文档】 |
| **自动化** | 定时任务（cron / 间隔 / 一次性）+ Webhook 触发 | 【文档】 |
| **团队资产归属** | Agent、Persona、记忆、工具、产物归 Workspace，不随人离职消失 | 【文档】 |

### 2.2 **完全不具备的**（我逐项查过）

| 缺失能力 | 验证方式 |
|---|---|
| ❌ 表单设计 / 动态表单 | README 全文无相关表述 |
| ❌ 审批流 / 会签 / 加签 / 转办 | 同上 |
| ❌ 业务台账（工资台帐、党员台账、工会台账） | 同上 |
| ❌ 业务状态机（草稿→审批中→已完成→归档） | 同上 |
| ❌ 数据权限分级（按部门/项目部/金额裁剪） | 只有 org/workspace 两级角色 |

> README 里「流程」只出现 1 次，指的是「Agent 处理文档、数据和跨系统任务的流程」，**不是 BPM 审批流**。这是最容易误读的地方。

### 2.3 运行成本（重要，决定适合的规模）

**【文档】OpenSandbox 是必需组件**——「It is a required part of every deployment」，Docker Compose 和 Helm 都默认包含。

完整依赖栈：**PostgreSQL + Redis + rustfs + Tempo + OpenSandbox**。即便最小部署（Docker Compose 单机）也要跑起这一整套。

**含义：它不是一个能塞进现有系统的轻量组件，而是一套需要独立运维的基础设施。**

## 3. 适合做什么（按匹配度排序）

### ★★★ 第一梯队：长期、有状态、产出交付物的工作

这类场景同时满足三个条件：**任务跨多天、需要真实文件/代码、成果要复用**。

| 场景 | 为什么适合 | 它用到的能力 |
|---|---|---|
| **技术调研与原型验证** | 要跑代码、要留现场、要产出可看的东西 | 持久沙箱 + 代码执行 + Artifacts |
| **数据分析与报表生成** | 从原始数据到可交付表格，反复迭代 | 沙箱 + Artifacts 版本化 |
| **文档站 / 内部知识产品构建** | 建站、预览、迭代，第二天接着做 | Artifacts 预览 + 持久化工作树 |
| **多系统数据核对与清洗** | 跨系统拉数、比对、出报告 | MCP 工具 + 沙箱 + 定时任务 |
| **持续性的爬取 / 监控 / 巡检** | 需要定时跑、要留历史 | 定时任务 + 持久沙箱 |

**共同特征**：工作本身就是「动手做东西」，而 AI 恰好能干。

### ★★ 第二梯队：团队共享的 AI 助手（偏问答与检索）

| 场景 | 适合度 | 注意 |
|---|---|---|
| 团队共用的知识问答助手 | 适合 | 靠 MCP 接内部知识库 |
| 跨 IM 的统一 AI 入口 | 非常适合 | 这是它的强项，六个 IM 渠道开箱即用 |
| 新人入职引导 / 规范查询 | 适合 | 靠三层记忆 + 技能 |

**为什么排第二**：这类场景其实用轻量方案（一个 RAG 服务 + IM 机器人）就能覆盖，用 CubePlex 属于「用基础设施解决单点问题」。

### ★ 第三梯队：有条件适合

| 场景 | 前提条件 |
|---|---|
| 自建企业 AI 平台的底座 | 你愿意接受它的 org/workspace 两级权限模型，且不再需要业务表单/审批 |
| 替代 SaaS 版 AI 工具（数据不出内网） | 你能承担 Postgres+Redis+rustfs+Tempo+OpenSandbox 的运维 |
| 给非技术团队配「数字同事」 | 业务本身是「做东西」而非「走流程」 |

## 4. 不适合做什么

### ❌ 1. 业务管理系统（含表单、审批、台账）

**这是它最不适合、也最容易被误用的方向。**

理由：
- 它没有表单引擎、没有审批流引擎、没有业务台账模型。【实测：README 无任何相关能力】
- 它的权限只有 Organization / Workspace 两级角色，**没有「按项目部裁剪数据」这类业务级数据权限**。
- 它的状态模型是「对话 + 消息线程」，**不是业务实体状态机**。

> 这条结论直接对应你上一轮的问题：**综合管理工作台**这类「人力/办公室/党建/工会」系统，核心是审批流和台账，用 CubePlex 承接等于用错的工具。

### ❌ 2. 需要严格数据权限隔离的系统

它的隔离粒度是 **Workspace**（工作区级）。如果你的要求是「同一工作区内，A 项目部的人看不到 B 项目部的数据」，它做不到——这需要业务级数据权限，得自己在 MCP 工具里实现。

### ❌ 3. 低延迟、高并发的在线业务接口

它是「人机协作平台」，不是「业务 API 网关」。对话式交互天然不适合承接高频交易类请求。

### ❌ 4. 轻量场景 / 资源受限环境

单机最少要跑 5 个组件（含 OpenSandbox）。**如果只是想要一个「能问答的机器人」，用它属于严重过度设计。**

### ❌ 5. 强合规审计场景（未经二次开发）

它审计能力有（工具调用、成本），但**凭证交给它的 org/workspace 两级模型**，若你的要求是「按业务实体逐笔留痕、可追溯到具体审批人」，需要自己补。

## 5. 一张判断表（怎么快速决定）

问自己四个问题，全部答「是」才适合：

```
1. 这项工作的产出是"东西"（文件/代码/网站/报表），而不是"一条审批记录"？
        │
        ├─ 否 → 不适合，你要的是业务系统
        └─ 是 ↓

2. 这项工作需要跨越多次会话、多天持续进行？
        │
        ├─ 否 → 不适合，一问一答用轻量方案即可
        └─ 是 ↓

3. 需要一个真实的执行环境（跑代码、装依赖、留文件）？
        │
        ├─ 否 → 不适合，纯对话不需要沙箱
        └─ 是 ↓

4. 你能承担 Postgres+Redis+rustfs+Tempo+OpenSandbox 的运维？
        │
        ├─ 否 → 不适合，考虑轻量替代
        └─ 是 → ★ 适合
```

**简化版一句话**：**「团队要一起做东西，而且这东西要做很久」→ 适合 CubePlex；「团队要走流程办事」→ 不适合。**

## 6. 与相近方案的边界

| 方案 | 它擅长 | 与 CubePlex 的分界 |
|---|---|---|
| **CubePlex** | 团队共享的长期 Agent + 持久执行环境 | 产出交付物、跨会话、有沙箱 |
| **Dify / Coze 类** | 按场景搭建的 AI 应用 | 一次性编排、无持久工作区 |
| **Dify 等 Workflow Canvas** | 可视化流程编排 | CubePlex 明确提出「不能退化为 Workflow Canvas」 |
| **业务系统（含审批流）** | 表单、审批、台账、数据权限 | CubePlex **完全不做这一层** |
| **DeerFlow / 个人 Agent 环境** | 个人使用的 Agent | CubePlex 面向团队、状态归组织 |

> CubePlex 自己的官方对比文章也把「长期工作的 Agent」vs「按场景构建的 App」作为核心区分。**这个自我定位是准确的。**

## 7. 对你（综合管理工作台）的具体结论

结合前一轮评估，直接回答：

| 你的需求 | CubePlex 是否适合 |
|---|---|
| 人力/办公室/党建/工会的审批与台账 | ❌ **完全不适合**——它没有表单、审批流、台账、数据权限 |
| 想给工作台加一个 AI 助手 | ⚠️ **不必用 CubePlex**——一个走 MCP/HTTP 的 RAG 助手就够 |
| 想给团队配一个能做技术工作的 AI 同事 | ✅ **适合**——但这是另一个项目，不是改造现有工作台 |
| 想借鉴它的边界治理思想 | ✅ **适合**——凭据排除、审计下沉、权限前置，这三条可以直接搬 |

**一句话**：**CubePlex 适合「新建一个 AI 同事」，不适合「改造一个业务系统」。** 你现在的项目属于后者。
