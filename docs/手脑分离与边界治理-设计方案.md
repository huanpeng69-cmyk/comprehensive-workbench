## 1. 先给结论

**你这个项目当前是「脑手同体」，而且它的形态与 CubePlex 那篇文的场景不完全一样——不能照搬它的重架构。**

三条实测事实决定了方案形态：

1. **工具在脑进程内同步执行。** `AgentTool.execute(Map) → String` 是普通函数调用，`AgentService:239` 直接 `tool.execute(args)`。没有独立执行环境、没有超时控制、没有执行前权限校验。**【代码实测】**
2. **项目里没有任何沙箱/隔离代码。** 全仓搜索无 `sandbox`/`Docker`/`ProcessBuilder`/容器编排痕迹。**【代码实测】**
3. **但你的风险面比 CubePlex 小得多。** 现有工具只有一个 `KnowledgeBaseTool`（HTTP 只读检索），**没有 shell、没有文件写、没有代码执行**。真正的高危操作（审批、发布、工资）都还没接进 Agent。**【代码实测】**

**因此正确的做法不是「上 K8s 沙箱」，而是抢在高危工具接入之前，把边界契约定死。** 现在改成本极低；等 `approve_leave`、`publish_salary`、`send_notice` 这类工具接进来之后再改，就是数据模型级返工。

### 已发现的四个真实缺陷（按风险排序）

| # | 缺陷 | 位置 | 风险 | 来源 |
|---|---|---|---|---|
| **D1** | **AI 密钥明文存库**。`ai_config.api_key` 是 `VARCHAR(512)` 裸字符串，无加密 | `ai/domain/AiConfig.java:40-41` | 数据库泄露/备份外流 = 模型额度被盗刷；有 DB 读权限即可拿到 | 【代码实测】 |
| **D2** | **工具调用无权限校验**。`/api/ai/writing/agent` 只继承全局 JWT 过滤，方法上无 `@PreAuthorize`；`AgentService` 内部也不再校验 | `ai/api/WritingController.java:44` | 任何登录用户都能让 Agent 调用全部已注册工具，绕过模块级数据权限 | 【代码实测】 |
| **D3** | **审计是「事后一根总账」**。`auditService.log` 在**整个循环结束后**才调用一次（`:257`），记的是「用了 Agent，未记录对话正文」。**工具名、参数、结果、是否失败全都没记** | `ai/application/AgentService.java:257` | 出事无法追责：不知道谁调了哪个工具、传了什么参数、拿到了什么数据 | 【代码实测】 |
| **D4** | **工具执行无超时、无取消、无失败隔离**。工具是同步阻塞调用；SSE 断了（`:241` 返回）也不会中断已在跑的工具 | `AgentService.java:228-242` | 知识库慢查询会占满线程池（8 线程），把整个 Agent 入口拖死 | 【代码实测】 |

> 另外：`AgentService` 第 239 行的 `tool == null` 分支只回「【未知工具】」，**这其实是正确的**——模型幻觉出的工具名不会被执行。这点做对了，保留。

## 2. 你项目的「脑」和「手」在哪

### 2.1 现状映射（对照实际代码）

```
┌─ 接入层 ─────────────────────────────────────┐
│ WritingController  /api/ai/writing/agent      │  【代码实测】
│   └─ 无 @PreAuthorize，仅全局 JWT             │  ← D2
└──────────────────────────────────────────────┘
                    ↓
┌─ 脑：AgentService（434行，Spring 进程内）─────┐
│ • while-loop：MAX_AGENT_ITERATIONS = 6        │
│ • 决策调用 chatNonStream → 有 tool_calls？    │
│ • 上下文：systemPrompt + memory 块 + history  │
│ • 线程池 8/8 + 队列16，AbortPolicy            │
│ • System Prompt 上限 8000，正文 30000         │
└──────────────────────────────────────────────┘
        ↓ 同步函数调用（← 边界缺失）
┌─ 手：ToolRegistry → AgentTool.execute() ─────┐
│ 目前只有 KnowledgeBaseTool                    │
│   └─ RestTemplate POST /api/query            │
│   └─ 头 X-Kb-Service-Token（服务令牌在进程内存）│
└──────────────────────────────────────────────┘
```

### 2.2 划分判据（三条，按你项目现实调整）

| 判据 | 问题 | 归「脑」 | 归「手」 |
|---|---|---|---|
| **数据权限** | 这段逻辑要不要按 `project`（项目部）/角色裁剪数据？ | 是（有 SecurityContext） | 否 |
| **爆炸半径** | 出错影响一个会话，还是污染业务数据？ | 只读、可回滚 | 会写库、会外发 |
| **可逆性** | 失败能否靠重试/撤回恢复？ | 能 | 不能 |

**关键结论**：**你项目里「手」的职责不是「跑 shell」，而是「代表某个具体用户去访问外部资源与业务数据」。** 这比 CubePlex 的沙箱问题轻，但比它多了 CubePlex 没有的东西——**多项目部的数据隔离**。这是你的边界治理真正的核心。

## 4. 边界如何定义与约束

### 4.1 三个必须补的边界

#### 边界一：脑 ↔ 手（工具执行）

| 项 | 内容 |
|---|---|
| **契约** | 脑只能通过 `ToolInvoker` 调工具；工具不得回读 SecurityContext（身份由脑显式传入）；工具失败必须降级为文本，不得抛异常打断循环（`AgentTool` 注释已规定 ✅） |
| **强制手段** | ① 执行前 `@PreAuthorize` 式校验；② 执行前写审计（pending），执行后写结果（success/failed）；③ 每个工具独立超时；④ SSE 断连即取消 |
| **检查点** | 工具执行日志能回答「谁、何时、用哪个工具、什么参数、拿到多少数据、成功与否」 |
| **违反信号** | 审计里只有 `AI_AGENT` 一条总账而看不到工具明细 ← **你现在的状态** |

**实现落账（2026-11-06，第三批修复）**：identity（username）与角色码（roleCodes）统一由 `AgentService`
在**主线程**从 `CurrentUserHolder` 取出，作为显式参数传给 `ToolInvoker`；`ToolInvoker` 内部绝不读
`SecurityContextHolder`。原因是工具跑在线程池里，ThreadLocal 不跨线程传递——此前执行器在工具线程
回读上下文，角色恒为空，任何声明了 `requiredRoles` 的工具都会被判「无权限」（当时无工具声明，
属潜伏缺陷，同线程写测试还把它掩盖了）。护栏：
`ToolInvokerTest#rolesComeFromCallerNotFromSecurityContext`（上下文设 HR、传参给 ADMIN，必须判无权限）。

#### 边界二：凭据 ↔ 数据

| 项 | 内容 |
|---|---|
| **契约** | 模型 API Key、KB 服务令牌不得以明文落库、不得进日志、不得下发前端 |
| **强制手段** | ① `ai_config.api_key` 改为加密存储；② `AiConfigView` 只回掩码（**现状已是**——`AiConfig.java` 注释写明「接口返回时一律脱敏」）；③ 日志不打印 headers |
| **检查点** | `SELECT api_key FROM ai_config` 拿到的不是可用密钥；前端 F12 看不到明文 |
| **违反信号** | 数据库备份泄露即可盗刷模型额度 ← **你现在的状态 D1** |

#### 边界三：项目 ↔ 项目（数据隔离）★ 你项目独有

| 项 | 内容 |
|---|---|
| **契约** | 所有业务模块按 `project`（项目部）隔离（README §4.2 已定）；Agent 作为「代客操作者」必须继承发起人的项目范围，不能放大 |
| **强制手段** | 工具执行前用 `DataScopeResolver` 注入当前用户的 `projectIds`，工具只允许查该范围 |
| **检查点** | 江湾项目部的用户，让 Agent「查一下云岭项目部的工资」，必须被拒或被裁剪 |
| **违反信号** | 工具的 SQL/查询没有 project 过滤条件 |

> **这是我认为你项目里最该优先做的一条。** CubePlex 那篇文章完全不涉及这个维度（它是通用平台），但你的 `README §4.2` 明确写了「所有业务模块按 project 做数据隔离，跨项目部查询需显式授权」。**Agent 一旦成为代客操作者，就是这条规则的漏洞口。**

> **实现落账（2026-11-06，项目范围真判定）**：`ToolInvoker` 已把 `needsProjectScope` 从「只记审计」改为真拒绝——工具声明为 `true` 时，调用者既无项目部（JWT `projectId`）又无全公司范围（`DataScopeResolver#hasCompanyScope`）即回 `【无权限】` 并留 `DENIED/403` 审计，不进工具实现。身份由主线程打包成不可变快照 `ToolCaller` 传入工具线程（工具线程**不得**回读安全上下文），`AI_TOOL_CALL` 审计同时记录 `projectId / companyId / companyScope`。**尚未做的是「注入 `projectIds` 让工具自己过滤」**：当前没有工具消费它，先把判定与透传做实，等第一个需要项目范围的工具接入时再补注入通道（届时还要防模型伪造同名 `args` 键）。护栏用例：`ToolInvokerTest#projectScopeTool*`、`ToolCallerTest`、`AgentServiceCallerTest`；决策记录见 ADR-M014。上线零行为变化——唯一在册工具 `query_knowledge_base` 已声明 `needsProjectScope=false`。

### 4.2 边界的「三层约束」落地法

任何边界按三层实现，缺一层不算边界：

1. **声明层**：规则即数据。工具元信息里声明 `requiredRoles`、`requiredPermission`、`needsProjectScope`、`sideEffect`（只读/可写/不可逆）。
2. **判定层**：纯函数 `ToolPolicy.canInvoke(user, tool, args)`，无 I/O，可单测。
3. **执行层**：Spring Security `@PreAuthorize` + `DataScopeResolver` 兜底，不依赖上层逻辑正确。

**关键**：判定层不能是唯一防线。工具自己也要做范围校验（执行层兜底），防止有人绕过判定层直接调工具。

## 5. 落地方案（分 4 阶段，每阶段可独立验收）

> 按 AGENTS.md「人工断点」原则：每个阶段做完停下来汇报，验收通过再进下一阶段。**不一次性全做。**

### P1：止血（1~2 天）— 修 D1、D2、D3

**不引入新架构，只补三处缺口。**

1. **密钥加密**（D1）
   - 新增 `AiConfigCrypto`：用现成的 Spring `TextEncryptor`（`Encryptors.delText(password, salt)`），密钥从环境变量读（`workbench.ai.crypto-key`）。
   - `AiConfigService.resolve()` 读出时解密；`save()` 写入时加密。
   - 迁移：加一列或加前缀标记（如 `ENC(...)`），启动时把旧明文加密回写。
   - **注意**：这是改配置+改数据，按 AGENTS.md 第 7 条**属于三道闸**，动手前我会先给你迁移脚本和回滚方案等你确认。

2. **Agent 入口加权限**（D2）
   - `WritingController.agent()` 加 `@PreAuthorize("hasAnyRole('ADMIN','MANAGER','EMPLOYEE')")`（按你现有角色调整）。
   - `AgentService.streamAgent()` 内，在**每次工具调用前**校验：该用户是否有权使用该工具。

3. **审计下沉到每次工具调用**（D3）
   ```java
   // 现在（:257）：循环结束后一根总账
   // 改为：调用前 + 调用后各一条
   auditService.log(username, "AI_TOOL_CALL", name,
       "调用参数摘要: " + summarizeArgs(args), "开始执行");
   String result = tool.execute(args);
   auditService.log(username, "AI_TOOL_RESULT", name,
       "结果长度: " + result.length(), "执行完成");
   ```
   - 参数与结果**摘要 + 截断**，不落全文（避免把敏感数据再存一份）。

**P1 验收**
- [ ] 数据库中 `api_key` 不是可用明文
- [ ] 无权限用户调 `/agent` 返回 403
- [ ] 审计表能查到每次工具调用的工具名、时间、用户、参数摘要

### P2：边界契约（3~5 天）— 消除 D4，建立「手」的抽象

1. **工具元信息升维**：给 `AgentTool` 加默认方法（不破坏现有实现）
   ```java
   default Set<String> requiredRoles() { return Set.of(); }
   default boolean readOnly() { return true; }          // 默认只读
   default boolean needsProjectScope() { return true; }
   default int timeoutMs() { return 15_000; }
   ```
   现有 `KnowledgeBaseTool` 全部走默认值即可，零改动。

2. **引入 `ToolInvoker`（脑与手之间唯一的横向通道）**
   ```
   脑 (AgentService) → ToolInvoker → [策略校验 | 审计 | 超时 | 取消] → AgentTool
   ```
   - 超时用 `CompletableFuture.orTimeout` + 独立小线程池（**不要**用 `AgentService` 那 8 个线程，工具慢查询会拖死入口）。
   - SSE 断连时置取消标志，工具感知后放弃。

3. **项目范围注入**
   - `ToolInvoker` 调工具前，把 `DataScopeResolver` 解析出的 `projectIds` 放进参数上下文。
   - 工具实现里**必须**用它过滤查询。

**P2 验收**
- [ ] 知识库超时不拖垮 Agent 入口（并发压测：8 个慢查询下第 9 个请求仍能正常回）
- [ ] SSE 断开后工具执行被中断，日志可见
- [ ] 江湾用户通过 Agent 查云岭数据 → 被裁剪或拒绝

### P3：长任务与「假装完成」（按需）

**只有当你要接「会跑很久的工具」时才需要做。** 你现在没有这类工具，所以**建议缓做**——这是文章最精彩的部分，但对当前项目是过度设计。

若要做，最小实现：

| 机制 | 做法 | 为什么需要 |
|---|---|---|
| 长任务脱钩 | 工具执行超 N 秒 → 转为后台任务，SSE 先回「已转后台」，完成后推送 | 网关 60s 超时会掐断 SSE |

| 世代栅栏 | 每次执行带单调递增 `executionId`，取消只作用于匹配的那个 | 防旧的 Stop 晚到误杀新任务 |

> ⚠️ 提醒：X 文章把「代际栅栏」列为 CubePlex 已有能力，**但我实读其开源代码后发现并没有这个实现**（那里的 `generation` 指的是出网凭据代际）。所以这条要自己设计，别以为能抄。

## 7. 需要你确认的三个决策点

按 AGENTS.md 第 1 条，涉及多种做法，先等你定：

**Q1｜P1 的密钥加密要动数据库，属于破坏性操作（第 7 条三道闸）。**
- 方案 A：新增列 `api_key_enc`，双写过渡，验证后删旧列（安全但两步）
- 方案 B：就地加密，加 `ENC(...)` 前缀，启动时批量迁移（一次到位，回滚要恢复备份）
- 你倾向哪个？我动手前会先给出迁移脚本 + 回滚步骤。

**Q2｜工具权限粒度按什么划？**
- 方案 A：按角色（ADMIN/MANAGER/EMPLOYEE）——简单，但粒度粗
- 方案 B：按「权限点」（如 `ai.tool.query_knowledge_base`）——细，但要扩权限表
- 方案 C：先按角色，工具声明 `requiredRoles`，后续再细化——**我推荐这个**

**Q3｜P3（长任务/Todo 契约）现在做还是缓做？**

## 8. 一页速查

**你现在的真实状态**：一个良性的「阶段 1.5」——Agent 循环写得不差（迭代上限、内容截断、记忆降级、未知工具拒绝都做了），但**四个安全边界全是空的**：密钥明文、入口无鉴权、审计是总账、工具无超时。
