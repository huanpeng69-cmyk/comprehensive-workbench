# 用户长期记忆接入决策（2026-10-15）

## 背景

工作台的 AI 写作台与 Agent 对话每次请求都从零开始：用户说过的偏好、单位口径、业务约定无法跨会话保留，用户必须反复重申。需要一套按用户隔离的长期记忆：能写入、能召回、能在对话时注入模型，并且不能跨用户或跨单位泄露。

## 备选方案

1. 向量检索（pgvector / 独立向量库）：语义召回质量最好，但要引入扩展、嵌入模型服务和新的运行依赖，当前阶段成本与收益不匹配。
2. 直接全量注入：实现最简单，但记忆条数增长后必然挤占上下文，也无法控制 token 预算。
3. 把记忆塞进 `sys_user` 表的新列：省一张表，但记忆是可变长的多条列表，塞进用户主表会破坏身份域边界（业务模块不得直接读写 identity 库）。
4. 新建 `memory` 模块 + 关键词/时间衰减/重要性打分检索 + 抽取式压缩 + 注入系统提示词：零新增依赖，同步可返回，预算可控。

## 决策与原因

选择方案 4。关键词与结构化打分在同一事务、同一进程内完成，不需要额外服务，也不会因为外部模型调用失败而拖垮对话链路；压缩采用抽取式（按句子命中情况截取原文），不做模型摘要，避免摘要失真和同步延迟。

关键约定：

- 归属键为 `(company_id, owner_username)`，取登录态里的单位与用户名，不查身份库。列表、召回、删除全部带这两个条件，物理上不可能读到别人的记忆。
- 新表 `user_memory`（Flyway `V16__user_memory.sql`）：`memory_type` 区分语义/程序/情景记忆，`importance` 0–100，`source` 区分用户手写与 AI 沉淀，`content_hash`（SHA-256）配唯一索引保证同一用户重复写入同一内容是幂等合并而不是报错，`expires_at` 支持过期自动失效。
- 召回打分 = `0.6 × 关键词相关度 + 0.4 × 重要性`，再乘时间新鲜度 `0.5^(距更新天数/30)`；同分按 id 倒序，保证输出稳定可测。
- 压缩受两个预算约束：条数 `topK`（默认 8）与 token 预算（默认 600、上限 2000）。逐条展开时单条最多 200 字，超出预算的条目折叠为摘要，并在 `omittedCount` 中给出未展开条数。
- 注入位置是系统提示词，不是用户消息：记忆是背景约束，不是用户本轮说的话。注入在主线程完成（工作线程没有 SecurityContext），检索失败只记 `warn` 日志并跳过注入，不影响本轮对话。
- 读路径与写路径不对称（沿用项目既有约定）：读（列表、召回）在无法确定归属时返回空，写（新增、删除）在无法确定归属时拒绝并记 `ACCESS_DENIED` 审计。

## 修改契约（PUT /api/memories/{id}）

记忆要能被真正修改，因此除了「删旧建新」之外补一个按 id 的更新接口。约定如下：

- 请求体 `MemoryUpdateRequest`：`content`（必填，≤1000）、`type`（可空）、`importance`（可空，0–100）、`ttlDays`（可空，0–3650）。
- 用 PUT 而不是 PATCH：请求体是「这四个字段的目标状态」而不是局部补丁，前端总是把当前值回传，语义更集中、更好校验。
- `ttlDays` 与新增时语义不同：新增要求 1–3650（可空 = 永不过期）；修改时 **null = 保持原有有效期不变**，`0` = 改为永不过期，`N` = 从现在起 N 天（不基于旧到期时间累加）。前端表单留空即对应 null。
- 修改后总是重算 `content_hash` 并刷新 `updated_at`：哈希是去重键的一部分，`updated_at` 是召回新鲜度衰减的依据。
- 撞车报错而不是静默合并：若改后的正文撞上该用户另一条记忆的哈希，返回 400 提示「已存在内容相同的<类型>，请直接修改那一条」，不做幂等合并——合并会让用户刚编辑的那条凭空消失。新增路径仍保持幂等合并。
- 归属隔离与删除一致：id 不存在或不属于当前用户，一律抛 `EntityNotFoundException` → 404，不区分「不存在」与「无权限」，避免成为探测别人记忆 id 的通道。
- 审计记录 `MEMORY_UPDATE`，目标类型沿用 `USER_MEMORY`，摘要形如「修改语义记忆，重要度 70：<前 40 字>」。
## 运行配置

不需要新增环境变量。迁移随后端启动自动执行；需要回退时执行 `server/src/main/resources/db/rollback/V16__rollback.sql`，它会先判断表存在再删除并打印提示，该脚本会删除全部用户记忆数据，属于不可逆操作。

## 后续约束

- 记忆的读、写、删都必须带 `company_id + owner_username`，不允许出现只按 id 查询的对外接口。
- 召回路径只读不写，不因召回更新访问计数或 `updated_at`，否则会让时间衰减失真。
- `omittedCount` 只统计「超出 token 预算而未展开」的条数，不统计被 `topK` 截断的条数；前端做「召回预览」时要自行按返回条数与 `topK` 判断截断。
- 记忆注入失败必须降级为「无记忆」继续对话，不得让记忆链路成为对话可用性的单点。
- 单用户记忆条数上限 200，超限时按「重要性最低、更新时间最旧」淘汰；调整上限需同步评估淘汰策略。
- 未来若改为向量召回，必须保持现有归属键、预算参数与 DTO 契约不变，只替换打分实现。
