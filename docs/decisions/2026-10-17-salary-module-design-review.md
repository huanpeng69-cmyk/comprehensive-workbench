# 工资制作模块设计评审与重构方案（2026-10-17）

> 依据：真实工资表 `广州红茶项目2026年9月工资(加个税).xls` 全量公式提取与数值反证 +
> 现有代码只读勘察。所有结论都带证据位置，未核实项单列。

## 0. 一句话结论

现在的「工资制作」不是核算系统，而是**把 Excel 工资表搬进数据库的搬运器**：后端零计算（金额一律
`varchar` 存 `=公式` 文本），计算散在前端公式引擎里，且只支持四则运算与 `SUM`。

按真实表格的公式形态来看，**工资表里根本不存在"通用公式计算"这件事**：整本工作簿 0 个
`IF/VLOOKUP/SUMIF/MAX/MIN`，全部是「基数 × 系数」和「加减」。真正需要引擎化的只有三样：
**社保代扣的量表、累计预扣个税、绩效激励的乘法链**。所以重构方向不是"造个更强的公式引擎"，
而是**把这三块领域算法固化进后端，把剩下的自由调整留给公式**。

## 1. 真实工资表的结构与公式（已实测）

### 1.1 工作簿结构

14 张表，分五类：

| 类别 | 表名 | 性质 |
|---|---|---|
| 汇总 | 红茶汇总 | 跨表引用各科室合计行 + `SUM` |
| 科室明细 | 计合、安全、财务、综合、物资、研发、城建 | 三层表头、逐人一行，**真正干活的地方** |
| 绩效 | 绩效 | 考核成绩 → 激励额度 |
| 派生报表 | 工资计提勿动、缴费表(勿动)、会费勿动、财务用表、预发绩效表（汇总） | 从明细跨表取数 |

三层表头（科室表）：

- 第 1 层：工资部分 / 应领工资额 / 扣款部分 / 实领工资额 / 领款人签字
- 第 2 层：岗位工资、专业技术职务津贴、加班、奖金、补差工资、年功工资、项目施工津贴、
  专项扣除、其他扣除、专项附加扣除、个人所得税、个人所得税调整、扣款
- 第 3 层：专项扣除下的 养老/失业/医疗/公积金/企业年金/大额医保；专项附加下的
  子女教育/继续教育/房贷利息/住房租金/赡养老人/婴幼儿照护费

### 1.2 核心公式（逐条实测，A1 记法）

列：D 岗位工资 · E 职务津贴 · F 加班工日 · G 加班费 · H 奖金 · I 补差工资 ·
J 年功工资 · K 项目施工津贴 · L 应领工资额 · M~R 六项代扣 · S~X 六项专项附加 ·
Y 个人所得税 · Z 个税调整 · AA 扣款 · AB 实领工资额 · AB3 当月天数（30）

```
L  = D+E+G+H+I+J+K                        ← 不含 S~X 专项附加
AB = L-M-N-O-P-Q-R-Y-Z-AA                 ← 不减 S~X、不减其他扣除
```

**口径要点：专项附加扣除（S~X）不进任何公式。** 它是独立"留档"列，只影响人工算出的 Y。
这与现行代码 `NET_FORMULA` 一致，但现行代码把 Y 当普通手填值，**实际上是把最需要算法的环节丢给了 Excel**。

### 1.3 三处必须引擎化的算法

**(1) 社保代扣 = 个人申报基数 × 固定比例（不是按当月工资算）**

逐行反推比例，跨 7 张科室表、22 行全部吻合：

| 项目 | 个人比例 | 证据 |
|---|---|---|
| 养老 | 8% | 基数 = 养老 ÷ 0.08 |
| 医疗 | 2% | 医保 ÷ 养老 = 0.25 恒定 |
| 失业 | 0.5% | 失业 ÷ 养老 = 0.0625 恒定 |
| 公积金 | 12% | 公积金 ÷ 养老 = 1.5 恒定 |
| 企业年金 | 2% | 年金 ÷ 养老 = 0.25 恒定 |
| 大额医保 | 定额 | 多数为 0 |

以梅春鹏为例（`计合` r8）：养老 802.8 / 失业 50.18 / 医保 200.7 / 公积金 1204 / 年金 201
→ 隐含基数 10035.00，且 `公积金÷基数=0.1200`、`医保÷基数=0.0200`、`失业÷基数=0.0050`、
`年金÷基数=0.0200`，四项同时精确命中。

**关键结论：基数与当月工资无关。** 岗位工资 5300 的人，社保基数是 10035
（`计合` r8 基数/岗位工资 = 1.89）。所以**"用工资乘比例"是错的**，必须独立存"社保申报基数"。
现行系统里这个基数根本不存在，六项代扣直接抄 Excel 的数值。

**(2) 个人所得税 = 累计预扣，公式完全没有**

- 全工作簿 Y 列（个税）**无任何公式**，19 个非零值全是手填常数。
- 没有起征点、没有税率表、没有速算扣除、没有专项附加参与。
- 现行前端 `taxThreshold: 5000` 是死配置（`salaryGradeStandard.ts`），无人调用。

**(3) 绩效激励 = `ROUND(激励部分 × 平衡系数, 0)`**

```
绩效表：I = ROUND(F 激励系数 × H 月度基数, 0)
        L = ROUND(I × J 平衡系数, 0)        ← 实测 J=0.9 的行 L=ROUND(I*0.9,0) 精确命中
        M = G + L（月度绩效总数，回填科室表 AE 列）
科室表：H 奖金 = 绩效!M{对应行}              ← 跨表引用
```

**配合度系数（K 列）恒为 0，且不进任何公式** —— 是废列。

## 2. 现行实现的问题（已逐条核实）

### 2.1 安全（最严重）

**P0-1 写接口缺数据范围闸门，PROJECT 用户可改全公司工资。**

证据链：

1. `SalaryService` 里 `assertCompanyScope` 只被调用 3 次：`listMonths`(L73)、`getConfig`(L243)、`saveConfig`(L251)。
2. 8 个写接口（`upsertMonth` L87、`deleteMonth` L126、`updateRecord` L137、`createRecord` L153、
   `deleteRecord` L180、`updatePerf` L191、`createPerf` L206、`deletePerf` L233）
   **只调 `writeOwnershipResolver.requireCompanyId`，不调 `assertCompanyScope`**。
3. `WriteOwnershipResolver.requireCompanyId`（L45-58）只解析"归属哪个单位"：projectId → 否则
   取 JWT 的 companyId → 两者都没有才拒绝。**它不判断数据范围。**
4. 所有账号 JWT 都带 companyId：`AuthService` L86 `jwtUtil.generate(..., user.getCompanyId(), ...)`，
   且 `V10__multi_company.sql` L159 已把 `sys_user.company_id` 收紧为 `NOT NULL`。
5. 因此 PROJECT 数据范围用户（项目经理、普通员工）能通过写闸门，对**本单位全公司**工资
   整月覆盖/删除/改单条。

对照组：`EmployeeService` 写路径 `assertCompanyScope`(L106) + `requireCompanyId`(L110) 两个都调，
并在 L127-129 注释「两者缺一不可」。

**被测试掩盖**：`SalaryServiceDataScopeTest` L100-108 断言 PROJECT 写被拒，但用
`SecurityContextFixture.runAs("pm", 7L, "PROJECT_MANAGER")`（L101），而 `runAs` 委托
`runAsInCompany(username, null, ...)`（Fixture L25）把 companyId 传成 **null**，
于是命中 `requireCompanyId` 的"两者都缺失"分支才被拒。**真实生产（带 companyId 的 PROJECT 用户）
无用例覆盖。**

**P0-2 配置表全局单行，任一单位可改写全公司薪档标准。**
`salary_config` 无 company_id（`V10` 明确"刻意不加"），`saveConfig` 只 `findById(1)`（L258-261）。

### 2.4 表格里存在、系统未建模的缺口

1. 社保申报基数 + 缴费基数上下限
2. 累计预扣个税所需的中间量：累计应纳所得额、已预缴税额、累计专项附加
3. 单位缴纳侧（企业部分）——表格本身也只有个人侧，属需求确认项
4. 应出勤天数（表头 AB3=30 天）、单位名称抬头、四级签字栏（部门负责人/财务/人力/制表人）
5. 会费计算（`ROUND(月标准工资 × 0.005, 0)`）
6. 预发绩效表（年薪人员 1-12 月）

8. 应领/实领的"合计与明细勾稽"校验（表格里手写 SUM，无自动核对）

## 3. 重构设计

### 3.1 职责划分：把"算"和"调"分开

核心判断：**真实数据证明工资表是"算法 + 手工调整"混合体**（同一列里既有 `ROUND(...)` 也有
`150+347` 这种硬拼）。所以不能走"全公式引擎"，也不能走"全硬编码"，要分三层：

| 层 | 职责 | 归谁 | 为什么 |
|---|---|---|---|
| **L1 领域算法** | 社保代扣、累计预扣个税、绩效激励、会费 | 后端 Java，可测 | 有法定/制度定义，必须可审计、可复算、可写单元测试 |
| **L2 字段取值** | 每人的岗位工资/津贴/奖金基数等 | 后端存值（`BigDecimal`）+ 可选表达式 | 表格显示这些是手工填的，本质是"输入" |
| **L3 勾稽关系** | 应领 = Σ工资项；实领 = 应领 − Σ扣款 | 后端固定规则，**不可用户改写** | 表格里 `L`/`AB` 全表同构，没有一个是特例 |

**关键取舍：L3 不允许用户自定义公式。** 现行系统让前端用 `=[岗位工资]+[专业技术职务津贴]+...`
这种字符串公式表达勾稽，收益为零、风险极高（一个标签打错就静默算错，且后端无法校验）。
真实表格里这两条公式 7 张表完全一致，直接固化成代码即可。

### 3.2 数据组织：从"一行 32 个字符串"到"输入 + 派生"

```
salary_month            月度批次（+ status、version、锁定）
salary_employee_input   每人输入项：工日、各项基数、绩效关联、专项附加、手工调整
                        —— 全部 DECIMAL(14,2)，单位分/元由列语义固定
salary_rate_config      费率与阈值，按 (company_id, 生效期间) 版本化
                        —— 养老8%/医疗2%/失业0.5%/公积金12%/年金2%、起征点5000、税率表
salary_si_base          社保申报基数（per 人 per 期间）+ 上下限
salary_calc_item        计算结果（每条来源 + 公式版本 + 金额），明细可追溯
salary_adjustment       手工调整项（正负号 + 原因 + 操作人），与算法结果分离
```

**为什么不保留"金额存字符串"**：那是为了保留 `=公式` 文本。重构后公式归后端，前端只拿数值，
`DECIMAL(14,2)` 才能保证「合计 = 明细之和」永远成立、且数据库能约束。

**为什么"输入"与"结果"分表**：真实表里 `150+347` 这种手工拼数是**输入**，
而 `ROUND(35*C*1.6,0)` 是**规则**。混在一列里就永远无法回答"这个数是怎么来的"。

### 3.3 公式计算的执行

```
1. 载入 salary_employee_input（当前批次）
2. 载入 salary_rate_config（按批次的生效期间命中唯一版本）
3. 逐人执行有序计算图：
   ① 工日 → 岗位工资 = 日工资标准 × 工日（若该人配置为公式制）
   ② 绩效激励链：激励部分 = 系数 × 基数 → 最终额度 = ROUND(×平衡系数) → 奖金
   ③ 应领 = Σ(L3 固定口径)
   ④ 六项代扣 = 社保申报基数 × 各比例（定额项按定额）
   ⑤ 应纳税所得额 = 应领 − 个人代扣 − 起征点 − Σ专项附加（按累计口径）
   ⑥ 累计预扣个税 = 累计应纳 × 适用税率 − 速算扣除 − 已预缴
   ⑦ 实领 = 应领 − Σ代扣 − 个税 − 手工扣款 + 手工补发
4. 全程 BigDecimal，setScale(2, HALF_UP)；仅在 ROUND(x,0) 的语义处 scale=0
5. 结果写 salary_calc_item，记录 rate_config 版本号
```

**执行方式的选择**：不用现成公式引擎（会引入解析器 + 标签映射 + 求值顺序一堆复杂度），
而是**手写有序计算步骤**。理由：步骤数固定（7 步）、依赖是固定的 DAG、每步都能单测。
将来若真需要用户自定义公式，再在 L1/L2 之外加表达式层，不影响现有结构。

### 3.4 结果校验（这是现在完全缺失的部分）

四道校验，全部后端执行、失败即拒绝保存：

1. **勾稽校验**：`应领 = Σ工资项`、`实领 = 应领 − Σ扣款`，容差 0.01。
2. **横纵对账**：明细合计 = 部门合计 = 汇总合计（对应表格的手写 SUM，物化后自动成立）。
3. **基准回归**：以真实 9 月表为黄金样本，重构后重算，逐人逐列比对，
   差异 > 0.01 即失败。**这是唯一能证明"重构没算错"的手段**，必须进 CI。
4. **异常拦截**：实领为负、必填项缺失、社保基数超上下限、个税与上年同期偏离过大
   → 不阻断但必须标红 + 记录原因，不允许静默通过（真实表已出现 4 个负实领）。

### 3.5 迁移建议（4 步，每步可独立上线）

1. **先修 P0 越权**（最小改动、独立提交）：给 8 个写接口补 `assertCompanyScope`，
   并补一条"带 companyId 的 PROJECT 用户写被拒"的测试。
2. **后端接管 L3 勾稽**：应领/实领改后端计算，前端公式退化为只读展示；`DECIMAL` 落库。
3. **引入社保基数 + 个税预扣 + 费率版本化**；导入时不再抄 Excel 的六项代扣与个税，改为算出来。
4. **加批次状态机与回归样本**；此时才谈"去 Excel 化"。

## 4. 需要你决策的 4 个问题

1. **单位缴纳侧（企业部分）要不要做？** 参考表只有个人侧，但工资总额/成本核算通常需要企业侧。
2. **个税是走累计预扣（年度累计）还是按月独立计税？** 前者才合规，但要求系统有全年连续数据；
   如果公司实际是财务手工算好再填，那第 3 步可以只做校验不做计算。
3. **社保基数从哪来？** 系统内维护 / 每次导入 Excel 带进来 / 从缴费表同步（那张表已有"养工号+金额"）。
4. **城建表那 4 个负实领怎么处理？** 是业务真实情况（人在城建但工资在别的项目发），
   还是表格笔误？这决定校验规则是"禁止负数"还是"允许负数但必须填原因"。
