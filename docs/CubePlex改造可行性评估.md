# 按 CubePlex 改造「综合管理工作台」的可行性评估

> 评估基准：`server` 157 个 Java 文件 / 18 个领域模块 / 17 个 Flyway 迁移 / 30 个测试类。
> **基线实测（本次已跑通）**：`mvn -o test` → **Tests run: 202, Failures: 0, Errors: 0, BUILD SUCCESS**；架构测试 `ModuleBoundaryTest` 4 条规则全部通过。
> 结论分档：**【实测】**= 本次运行/读码确认；**【推断】**= 基于代码结构的判断；**【建议】**= 设计意见。

---

## 1. 可行性结论（先说结论）

**结论：技术上可以改造，但不建议按 CubePlex 原样改造。建议只吸收其「边界治理」思想，放弃其「控制面/执行面分离」的工程形态。整体可行性判定为「部分可行，核心部分不可行」。**

拆开说：

| 维度 | 可行性 | 说明 |
|---|---|---|
| 吸收 CubePlex 的**边界治理思想**（凭据排除、审计下沉、权限前置） | ✅ **高度可行** | 与现有 Spring 架构天然契合，不破坏任何现有功能 |
| 照搬其**控制面 / 执行面分离**（Harness + 沙箱池） | ❌ **不可行** | 与「模块化单体」定位直接冲突，收益远小于成本 |
| 移植其**技术栈**（Python/FastAPI + CubeLoop） | ❌ **不可行** | 等于重写整个后端，违背「现有功能不变」的前提 |
| 借用其**Workspace 团队资产模型** | ⚠️ **部分可行** | 与现有 `identity` / `memory` 重复建模，需大改数据模型 |
| 借用其**Append-Only 状态机 + 长任务治理** | ⚠️ **当前不需要** | 你现在没有长任务场景，属过度设计 |

**一句话理由**：CubePlex 解决的是「**多人共享一台机器跑不受信代码**」的问题；你的系统解决的是「**组织内部一批人按项目部和角色办受控的业务事**」。前者的核心矛盾是**进程隔离**，后者的核心矛盾是**数据权限**。把前者的架构套到后者，是拿错了药方——你会付出巨大的改造成本，却解决不了你最真实的风险（跨项目部越权）。

## 2. 改造涉及的范围与主要改动点

以下按「与现有代码的接触面」分层列出。**接触面越大的越危险**。

### 2.1 范围总览

```
┌─────────────────────────────────────────────────────────┐
│ 层 1  吸收思想（改动小、收益高）        ← 建议做           │
│   凭据治理 · 审计下沉 · 权限前置 · 策略即数据              │
├─────────────────────────────────────────────────────────┤
│ 层 2  引入「手」的抽象（中等改动）      ← 有条件做          │
│   ToolInvoker · 工具元信息 · 超时/取消 · 项目范围注入      │
├─────────────────────────────────────────────────────────┤
│ 层 3  控制面/执行面物理分离（改动巨大）  ← 不建议做         │
│   独立沙箱服务 · 租约管理 · 持久卷 · 跨进程执行协议         │
├─────────────────────────────────────────────────────────┤
│ 层 4  技术栈替换（等于重写）            ← 不可行           │
│   Java/Spring → Python/FastAPI + CubeLoop                │
└─────────────────────────────────────────────────────────┘
```

### 2.2 层 1：吸收边界治理思想（改动点明细）

| 改动点 | 触及文件 | 改动量 | 风险 |

**判定：层 1 完全可行，且不改变任何对外行为。** 现有 202 个测试可作为回归护栏。

### 2.3 层 2：引入「手」的抽象（改动点明细）

| 改动点 | 说明 | 触及范围 |
|---|---|---|

**判定：层 2 可行，但有一个架构硬约束**——见 §3.3「ArchUnit 会立刻报错」。

### 2.4 层 3：控制面/执行面物理分离（若要照搬 CubePlex）

这是 CubePlex 的核心。若真要照搬，改动清单如下：

| 改动项 | 涉及 | 说明 |
|---|---|---|
| 拆出独立执行服务 | 新建服务（Java 或 Python） | 承载工具执行，独立部署 |

| 凭据边缘代理 | 新增 Broker 服务 | 占位符 → 真实令牌置换 |
| 前端 SSE 协议改造 | `aiWriting.ts` | 5 种事件可能需扩展 |

**判定：改动量约等于在现有单体外再造一个系统。** 按你当前 157 个 Java 文件的规模，这至少是 3~6 个月的工作量，且期间业务功能全部停滞。

### 2.5 层 4：技术栈替换

| 项 | 现状 | CubePlex | 迁移代价 |
|---|---|---|---|
| 语言/框架 | Java 17 + Spring Boot 3.3.5 | Python 3.12 + FastAPI | **重写全部后端** |
| Agent 框架 | 自研 `AgentService`（434 行） | CubeLoop | 重写循环 + 工具 + 中间件 |
| 数据访问 | Spring Data JPA | SQLAlchemy + Alembic | 17 个迁移全部重写 |
| 权限 | Spring Security + `@PreAuthorize` | 自研 RBAC | 重写 |
| 架构测试 | ArchUnit（4 条规则，已生效） | 无对应物 | **失去唯一自动化架构护栏** |

**判定：不可行。** 这不是「改造」，是「重写」，与考题前提「保持现有功能不变」直接矛盾。

## 3. 技术难点

### 3.1 难点一：身份在「脑」和「手」之间怎么传 ★最难

**这是整个改造最本质的难点，且 CubePlex 的方案不能直接套用。**

- 你的 `DataScopeResolver` 三个方法全部依赖 **JWT 里的身份**：`currentProjectId()`、`currentCompanyId()`、`hasCompanyScope()`。**【实测：读 DataScopeResolver.java】**
- 现有实现 `CurrentUserHolder.currentUsername()` **依赖 ThreadLocal**，`AgentService` 已经踩过这个坑——代码注释明写「安全上下文不会自动传到线程池，在主线程先取出用户名再传给 Agent 线程」（`AgentService.java:126-127`）。**【实测】**
- 一旦「手」跑在**独立进程/沙箱**里，ThreadLocal、SecurityContext 全部消失。

**这意味着**：任何跨进程方案都必须把身份**显式序列化**成令牌传给执行端，并重新建立可信链路。CubePlex 的做法是「沙箱不认识用户，只认识租约」，但**你的业务工具必须认识用户**——因为要按项目部裁剪数据。

**难点本质**：CubePlex 的「手」是无身份算力；你的「手」是**代客操作者**。这两者的信任模型根本不同，无法照抄。

### 3.2 难点二：权限前置会撞上现有 JWT 语义

- `JwtUtil` 只有 `expiration-minutes`，**没有吊销机制**（无 `jti`、无黑名单）。**【实测】** README 也承认「JWT 吊销」是遗留风险。
- 若按 CubePlex 的做法「每个动作都重新校验持久化授权」，需要**引入吊销/授权查询**，否则校验的只是同一张不可撤销的票。
- 更麻烦的是：你的工具是**同步函数**，一次 Agent 循环最长可跑 6 轮（`MAX_AGENT_ITERATIONS`）；期间管理员改了用户角色，当前实现完全无感。

**结论**：权限前置**可行但有前提**——要么补 JWT 吊销，要么在 `ToolInvoker` 里做一次实时授权查询。这是额外工作量，不是顺手就能改的。

### 3.3 难点三：ArchUnit 会立刻报错（这是好事，但会挡路）

现有 `ModuleBoundaryTest` 有 4 条硬规则，其中两条会直接拦住改造：**【实测】**

```
1. 模块之间不得直连对方仓储层
2. 底层模块不得依赖业务模块
3. 平台内核不得依赖业务模块
4. 只有平台适配层可直连身份仓储
```

- 若新增「执行服务」模块，**必须登记进 `ALL_MODULES`**，否则规则对它不生效（等于护栏失效）。
- 若执行服务要读用户身份，**只能走 `platform/identity` 适配层**，不能直连 `identity.repository`。
- 若拆成独立进程/独立工程，**ArchUnit 的 `@AnalyzeClasses(packages = "com.workbench")` 覆盖不到跨仓库依赖**——你会失去唯一的自动化架构护栏。

**这是双刃剑**：规则挡住你，说明它在起作用；但它也说明**任何跨仓库拆分都会让护栏失效**。

### 3.4 难点四：Flyway 迁移不可逆的累积

- 已有 17 个迁移（V1~V17）。**【实测】**
- CubePlex 引入的 Workspace / Session / EventDelta / SandboxLease 是**一批新表 + 新归属键**。
- 若按它的「所有资产归属 org + workspace」建模，需要给**已有的每一张业务表**加 `workspace_id`——涉及 `employee` / `salary` / `leave` / `party_fee` / `condolence` / `notice` / `memory` 等全部表。

**风险**：这类「给所有表加归属键」的迁移，一旦上线后发现问题，回滚等于全表数据回退。**这是最难回滚的一类改动。**

### 3.5 难点五：SSE 协议是隐式契约，前端只有一处但耦合很深

- 前端 `aiWriting.ts` 逐帧解析 5 种事件（`message` / `tool_call` / `tool_result` / `done` / `error`）。**【实测：aiWriting.ts:78-85】**
- CubePlex 的长任务治理要求「60s 后脱钩为后台任务」，会**新增事件类型**（如 `task_detached`）。
- 后端 `AgentService` 明确注释：「经 Node/Vite 代理时 HTTP 流关闭事件可能不透传，前端靠 done 帧结束状态」（`:262-263`）。**【实测】** 说明流式链路已经踩过坑。

**风险**：改 SSE 协议要前后端同步发版，且代理层行为需要重新验证。

## 4. 潜在风险

| # | 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|---|
| **R1** | **改造期间业务停滞**。层 3/4 是 3~6 个月量级，期间 202 个测试的护栏只能保护现状，不能保护「正在改的东西」 | 高 | 高 | 只做层 1/2，分阶段交付 |
| **R2** | **数据迁移不可逆**。给所有业务表加 `workspace_id`，回滚等于全表回退 | 中 | **极高** | 若必须做，先在分支 + 备份库验证 |
| **R3** | **失去 ArchUnit 护栏**。跨仓库拆分后架构约束无法自动验证 | 高（若做层 3/4） | 高 | 保留单仓库，或为每仓库单独建规则 |
| **R4** | **权限模型冲突**。CubePlex 的「租约无身份」 vs 你的「代客操作必须有身份」 | 必然发生 | 高 | 不复用其沙箱身份模型，自研 `ToolInvoker` |
| **R5** | **凭据泄漏面扩大**。执行端跑在别处，模型 Key / KB 令牌要跨网络传 | 中 | 高 | 采用其「占位符 + 代理置换」思路（这是它唯一真正值得抄的机制） |

| **R7** | **前端 SSE 兼容性回归**。代理层对长连接的处理未经验证 | 中 | 中 | 协议变更必须前后端同发版 + 灰度 |

### 特别提示：R2 是唯一「不可逆」风险

其他风险都能靠回滚代码恢复，**只有「给全表加归属键」这类迁移，回滚要恢复数据**。按 AGENTS.md 第 7 条三道闸，这类操作必须有备份 + 明确回滚路径才能动。

## 6. 最终结论与建议

### 6.1 结论

**「按 CubePlex 改造」这个命题本身需要拆解，否则会得出错误答案。**

- **可行的部分**：它的**边界治理思想**（凭据排除、审计下沉、权限前置、策略即数据）。这四个原则与框架无关，可以直接在你的 Spring 架构里落地，改动集中在 5~6 个文件，不破坏任何现有功能。
- **不可行的部分**：它的**工程形态**（控制面/执行面物理分离、沙箱池、租约管理、Append-Only 状态机）。这些是为「多人共享机器跑不受信代码」设计的，而你的场景是「组织内按项目部和角色办受控业务事」。
- **必须放弃的部分**：它的**技术栈**（Python/FastAPI + CubeLoop）。移植等于重写，且会让你失去 ArchUnit 这唯一的自动化架构护栏。

### 6.2 三条核心理由

1. **问题域不匹配**。CubePlex 的核心矛盾是进程隔离，你的核心矛盾是数据权限隔离。它的方案对你是「高成本、低收益」。
2. **改造成本与收益严重失衡**。层 3/4 需 3~6 个月且业务停滞，而收益（防 shell 逃逸、防宿主破坏）在你的场景里**根本不存在**——你没有 shell 工具、没有不可信代码执行。
3. **你会失去现有护栏**。202 个测试 + 4 条 ArchUnit 规则是你最宝贵的资产；跨仓库拆分会让它们大面积失效。

### 6.3 建议路线

**做层 1 + 层 2，不做层 3 + 层 4。**

| 阶段 | 内容 | 工作量 | 是否破坏现有功能 |
|---|---|---|---|
| P1 | 凭据加密、审计下沉、权限前置 | 1~2 天 | 否 |
| P2 | ToolInvoker、工具元信息、超时取消、项目范围注入 | 3~5 天 | 否（接口加 default 方法） |
| P3 | 长任务治理 | 推迟，无场景 | — |
| P4 | Workspace 资产化 | 不建议（与 identity 重复建模） | — |

**如果你确实想要「手脑分离」的物理形态**，有一个折中方案：**把 `ToolInvoker` 设计成可替换实现**——现在跑在进程内（`LocalToolInvoker`），未来若有真实需求（比如接入需要沙箱的代码执行工具），再实现 `RemoteToolInvoker` 走独立服务。这样**契约先立、实现可换**，用 5 天的成本买下未来 6 个月的选择权，而不是现在就付 6 个月的代价。
