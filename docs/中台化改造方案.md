# 综合管理工作台 · 企业中台化改造方案

- **状态**：方案（待评审，未改任何代码）
- **日期**：2026-10-13
- **目标形态**：服务公司**多个二级单位/分公司**的统一管理中台（软隔离）
- **关联文档**：`README.md`、`综合管理工作台技术方案与架构分层说明.md`（ADR-T001/T002）、`docs/Phase0-架构盘点报告.md`、`docs/decisions/2026-10-13-multi-org-middle-platform.md`
- **范围**：只做设计与文件级任务拆解，不动代码

---

## 0. 结论先行

1. **本项目已经具备中台内核的雏形**，缺的不是"服务拆分"，而是"能力沉淀 + 接入机制 + 多单位维度"。
2. **不建议为"中台"拆微服务**。`综合管理工作台技术方案与架构分层说明.md` 的 ADR-T001 结论依然成立：模块化单体 + 分层 + 可插拔适配层。
3. **多单位是本次最大的架构分叉，且比预想更硬**：现有 `sys_role.code`、`process_definition.code`、`salary_month.month` 都是**全局唯一**，`salary_config` 是**单行配置表**（`id integer primary key default 1`）。不做数据模型改造，"多个二级单位"根本无法落地。
4. **正确顺序是**：先有回归测试基线 → 再抽平台内核（唯一的数据权限实现）→ 再落多单位维度 → 再做能力中台与动态接入。反过来做会在流沙上盖楼。
5. **最大风险不是技术，是测试基线太薄**：全后端只有 3 个测试文件（都在 `ai` 模块），无法支撑平台级重构。

## 1. 中台的定义与本次目标

**中台 ≠ 微服务。** 中台是"把被多个业务域重复使用的能力抽出来、统一治理、标准化接入"。判据只有一条：

> 新增一个业务域，需要改多少公共代码、改多少前端代码、发几次版？

### 1.1 本次目标边界

| 维度 | 目标 |
|---|---|
| 服务对象 | 公司总部 + 多个二级单位/分公司（各自有项目部、部门、员工） |
| 数据隔离 | 单位之间**互不可见**；单位内按 `项目/部门/全公司` 分档 |
| 运维 | 一套部署、一套数据库（软隔离），预留可切换硬隔离的接入点 |
| 接入 | 新增业务域 = 加一个模块包 + 一份 Flyway 脚本，**前端零改动** |
| 权限 | 菜单级 / 接口级 / 按钮级 / 数据级四级权限，角色在**单位内**生效 |

### 1.2 明确不做（本期）

- 不拆微服务、不引入消息中间件（沿用数据库任务表）。
- 不上微前端（只有出现多团队独立发版需求时才评估）。
- 不重写流程引擎（现有的数据驱动设计够用，只需补公司维度与去掉硬编码审批人）。

### 2.3 多单位改造的硬障碍（本次最关键发现）

现有数据库里存在**跨单位必然冲突**的约束与结构：

| 位置 | 现状 | 多单位下的后果 |
|---|---|---|
| `V1__init_identity.sql:15` | `sys_user.username ... unique` | A 单位和 B 单位不能各有一个 `zhangsan` |
| `V1__init_identity.sql:28` | `sys_role.code ... unique` | 无法"每个单位各有一套 HR_ADMIN"；角色无法在单位内生效 |
| `V2__init_workflow.sql:4` | `process_definition.code ... unique` | 各单位不能有各自的审批流程定义 |
| `V4__init_salary.sql:7` | `salary_month.month ... unique` | 全库只能存在一个 `2026-10` 工资月 |
| `V4__init_salary.sql:12,55` | `salary_record.id` / `perf_record.id` 为 `varchar(64)` 主键（"月份-姓名"组合键） | 跨单位主键冲突 |
| `V4__init_salary.sql:76` | `salary_config.id integer primary key default 1` | **单行配置表**：全系统共用一份工资核算配置 |
| `WorkflowDataSeeder` | 接待流程 A/B/C 审批人写死具体用户名（`chenguodong` / `limingyuan` / `wanghaitao`） | 多单位下审批人直接串单位 |

同时，**部分业务表连 `project_id` 都没有**：`salary_month`、`salary_record`、`perf_record`、`salary_config`、`notice`、`party_fee` 均无。目前工资模块的做法是"整模块只允许 `COMPANY` 数据范围角色访问"（`SalaryService:66-73`，非公司级角色抛 `IllegalStateException` 并写 `ACCESS_DENIED` 审计）——这是粗糙但确实起作用的兜底，多单位下会变成"所有单位的工资都能被公司级角色看到"。

## 3. 目标架构

### 3.1 分层（在现有分层上增加"平台内核"与"接入契约"）

```text
展现层        web/ 动态路由 + 动态菜单（后端下发）+ 共享组件库
              ────────────────────────────────────────────────
接口层        api/  Controller：参数校验、权限点入口、统一错误码
接入契约      platform.module：ModuleDescriptor + BusinessModuleRegistry(SPI)
              ────────────────────────────────────────────────
应用层        <模块>/application：用例编排、事务边界
领域层        <模块>/domain：实体、状态流转、业务规则
              ────────────────────────────────────────────────
平台内核      platform/：DataScopeResolver、PermissionService、AuditPort、
              CodeGenerator（编号）、DictService、FileService、MessageService
基础设施      repository/、外部适配（AI 适配器、对象存储、Redis）
              ────────────────────────────────────────────────
数据层        PostgreSQL：所有业务表 + sys_* 表统一带 company_id
```

约束：**业务模块只依赖 `platform` 提供的接口，禁止在业务模块内重复实现数据权限、编号、附件、消息。**

### 3.2 平台能力清单（中台"货架"）

| 能力 | 现状 | 目标 |
|---|---|---|
| 统一身份与组织 | ✅ 有 | 增加 company 维度 |
| 统一权限（四级） | ⚠️ 仅认证 | 权限点表 + 菜单/按钮下发 + 数据权限统一实现 |
| 统一流程与待办 | ✅ 引擎可用 | 定义按单位隔离、审批人解析去硬编码、后台可配置 |
| 统一审计 | ✅ 骨架好 | 扩字段（ip/ua/风险等级/前后镜像）+ 审计中心页面 |
| 统一消息（站内信/回执） | ❌ 无 | 新建，复用现有抄送/待办链路 |
| 统一文件与附件 | ❌ 无 | 新建，统一上传/下载鉴权 + 审计 |
| 统一字典与编码 | ✅ 已建（2026-10-14，`codegen` 模块 + `CodeGenPort`，见 ADR-M009） | 后台规则维护（增删改）、按业务接入 |
| AI 能力网关 | ✅ 有雏形 | 提示词版本化、调用审计、敏感材料拦截 |
| 报表与指标 | ❌ 无 | 按需新建，优先复用导出能力 |

### 3.3 多单位隔离模型（软隔离，预留硬隔离切换点）

**选型**：同库同表 + `company_id` 列（软隔离）。理由与备选见 ADR。

**落库规则**：

1. 所有业务表与 `sys_*` 表增加 `company_id bigint not null`，并建索引 `(company_id, ...)`。
2. 现有数据统一回填为当前唯一公司的 id（迁移脚本内确定，不写死数字）。
3. 破坏全局唯一的约束改为**复合唯一**：
   - `sys_user`：`unique(company_id, username)`
   - ~~`sys_role`：`unique(company_id, code)`~~ → **本次未采用**（见更正 ②）：角色码全局统一，`code` 全局唯一
   - ~~`process_definition`：`unique(company_id, code)`~~ → **本次未采用**（见更正 ②）：流程定义三家单位共用一套，`code` 全局唯一
   - `salary_month`：`unique(company_id, month)`
   - ~~`salary_record` / `perf_record`：主键改为 `(company_id, id)` 或 id 加单位前缀~~ → **本次未采用**（见更正 ②）：主键保持 `id`，单位维度靠 `company_id` 列
   - ~~`salary_config`：单行表改为 `(company_id)` 分片，每单位一行~~ → **本次未采用**（见更正 ②）：保持全局单行，三家单位共用一份核算配置
4. 引用当前登录上下文的表（JWT）：增加 `companyId` claim，`CurrentUserHolder` 增加 `currentCompanyId()`。
5. 角色在单位内生效：`sys_user_role` 增加 `company_id`，或明确"用户所属公司决定其角色生效范围"（推荐后者，改动小）。
**更正 ②（阶段 2 实施后）**：落库规则 3 里只有两条真正落地（`sys_user` 与 `salary_month` 的复合唯一），其余四条**刻意不做**，与本文件 §9.1 结论 2（"是否要各单位的流程定义与工资配置 → 不需要，3 个单位共用一套"）一致：① `sys_role.code`、`process_definition.code` 保持**全局唯一**——角色码与流程定义由公司统一制定，不允许各单位各造一套；② `salary_record` / `perf_record` 主键**不改**（仍是 `id varchar(64)`，值是"月份-姓名"组合键），单位维度靠 `company_id` 列过滤，改主键会连带破坏前端既有键与已导入数据；③ `salary_config` 保持**全局单行**（`id integer primary key default 1`），V10 不给它加 `company_id`。**后果（如实记账）**：工资核算配置（应出工日基准 + 薪档标准）三家单位共用一份；若将来某单位要求独立配置，属新需求，须单独开 ADR 并做 `(company_id)` 分片迁移。

**为什么选软隔离**：一套部署、一份运维、迁移成本低，且现有 `org_unit` 顶层"公司"节点已存在，能自然承接。硬隔离（独立 schema/独立库）保留为**切换点**——只要所有表都规范带 `company_id`，将来抽库就是按列分片导出，不需要重写业务代码。

### 3.4 数据权限三档策略（统一实现）

| 策略码 | 语义 | 适用 |
|---|---|---|
| `PROJECT` | 本单位内仅本项目/本部门数据 | 花名册、请假、慰问金 |
| `COMPANY` | 本单位全部数据 | 单位 HR/财务/党务/工会负责人 |
| ~~`COMPANY_TREE`（新增）~~ → **本次未采用**（见下方更正 ①） | 原设想"本单位 + 下属单位" | 无 |

**实现要点**：把 `callerHasCompanyScope()` / `assertCompanyScope()` / `resolveProject()` 收敛为 `platform/DataScopeResolver`，业务模块只声明策略，不再各写一份。写操作越权统一走"拒绝 + 写 `ACCESS_DENIED` 审计"（沿用 `SalaryService` 已有的正确做法）。
**更正 ①（阶段 2 实施后）**：`COMPANY_TREE` **不新增**。`org_unit` 只能表达"公司（`type=COMPANY`）→ 项目部/部门"这一层，且每个二级单位把自己视为一个公司根节点，跨公司本就不允许可见；于是 `COMPANY` 档（`company_id = 登录态单位`）已经覆盖本期全部用例，再留一个"本单位 + 下属单位"的重叠档位，只会让后续改动误以为存在上下级授权。**将来若真要"集团公司看全部下级公司"，必须单独开 ADR，并先定义跨公司的上下级口径（当前表结构没有这一口径）。**

## 5. 实施路线

> 每阶段独立分支、独立提交；破坏性变更（改列、改约束、删文件）走"三道闸"（见第 7 节），缺一不可。

### 阶段 0｜回归测试基线【已完成 2026-10-13】

- **目标**：给现有行为上锁，让"重构后行为不变"这件事可验证。
- **实际交付**（全部落在 `server/src/test/`）：
  1. **数据权限 26 条**：`hr/EmployeeServiceDataScopeTest`(7)、`leave/LeaveServiceDataScopeTest`(5)、`condolence/CondolenceServiceDataScopeTest`(4)、`party/PartyFeeServiceDataScopeTest`(5)、`salary/SalaryServiceDataScopeTest`(5)。覆盖 G1 涉及的 5 个服务，以及 `PROJECT` / `COMPANY` / `PROJECT` 无 `projectId` / `COMPANY` 但 `enabled=false` 四种情形；越权一律断言"拒绝 + 写审计记录"。
  2. **安全层 12 条**：`security/JwtUtilTest`(6)、`security/JwtAuthFilterTest`(6)。

  2. **为什么拆两张表**：规则低频读、几乎不改；序号高频写、有并发争用。拆开后「改规则」不会因序号行锁阻塞，取号热路径也只碰一张小表（命中 `(category, period)` 索引，行锁粒度最细）。
  3. **不重号不跳号的实现**：取号在一个事务内用 `@Lock(PESSIMISTIC_WRITE)`（PostgreSQL `SELECT ... FOR UPDATE`）锁住序号行再递增，把同一 `(类别, 周期)` 的并发请求在数据库层串行化；`(category, period)` 唯一约束兜住并发建行。**不跳号靠两件事**：① 序号递增与事务同生共死，调用方业务回滚则序号一起回滚；② **先校验模板、再取号**——模板非法属配置错误，若放到取号之后判断，序号已被 `save` 消耗成空号（这条顺序由 `CodeGenServiceTest#templateIsValidatedBeforeAnySequenceIsConsumed` 锁定）。
  4. **边界口径**：类别不存在 / 已停用 → `IllegalArgumentException`（对外 400，不是 500）；`prefix` 为空则 `{PREFIX}` 替换为空串，服务不擅自补分隔符；序号超出 `seq_width` 时**不截断**（唯一性优先于格式）；序号表第一行在首次取号时创建，**V12 刻意不种序号数据**（否则首个业务编号被顶高）；序号表不设 `company_id`——文号是公司级编号，与 `salary_config` 保持全局的理由一致（§9.1 结论 2），单位维度由调用方在业务数据上落。
  5. **「不空号」与「不重号」的取舍（如实记账）**：`POST /api/codes/{category}/next` 支持提交前预取，文号一经取出即消耗；前端预取后若最终未提交，该号会成为空号。选择保住「不重号」，并要求调用方在真正落库前一刻取号。
  6. **验证**：`mvn -B -f server\pom.xml test` → **129 条单测全绿**（119 → 129，新增 `CodeGenServiceTest` 10 条）；`mvn -B -f server\pom.xml verify` → **129 + 17 集成全绿**（14 → 17，`SchemaBaselineIT` 迁移数 11 → 12 并新增 3 条 V12 契约断言），`BUILD SUCCESS`。`ModuleBoundaryTest` 已把 `codegen` 登记进 `ALL_MODULES`，模块边界规则对新模块生效。
  7. **本次实测发现并修复的缺陷（含根因）**：`CodeGenServiceTest#unknownPlaceholderIsRejectedInsteadOfLeakingLiteral` 抓到我第一版实现的真实缺陷——模板校验放在取号**之后**，序号已被 `save` 消耗。已把校验前移，并补 `templateIsValidatedBeforeAnySequenceIsConsumed` 断言"既不能读序号表也不能写序号表"锁住顺序。
  8. **集成测试的两个坑（防再犯）**：`SchemaBaselineIT.assertRejected(sql, state)` 的语义是「先成功插一次、再插一次断言被拒」，**只适用于"库里还没有该行"的场景**。我给 V12 写的两条误用了它：`code_sequence` 的 CHECK 约束是单次插入即失败、`code_rule` 的 `LEAVE` 已被 V12 种下（首次插入就冲突），两次都在第一次 `exec` 就抛异常。已改为直接 `assertThrows(SQLException.class, ...)`。另：断言"序号表必须为空"不能写 `count(code_sequence) = 0`——别的测试可能已取号留下序号行，**测试会互相依赖**；改为数一个从未被其它测试碰过的类别（`CONDOLENCE`）。

## 附二：Docker Engine 29 导致 Testcontainers 探测失败（阶段 0 实测根因）

**现象**：`mvn verify` 跑 `SchemaBaselineIT` 时报 `Could not find a valid Docker environment`，但 `docker ps` / `docker info` 一切正常。

**根因**：Docker Engine 29 / Docker Desktop 4.72 起，客户端声明的 API 版本低于引擎下限时，引擎**直接拒绝**请求。用原始 HTTP 探针访问 `npipe:////./pipe/docker_engine` 实测：`/v1.24/info` 与 `/v1.32/info` → `400 Bad Request`，`/v1.40/info` 及 1.43～1.54 → `200 OK`（即真实下限落在 1.33～1.40 之间）。而 Testcontainers 依赖的 docker-java **默认声明 API 1.32**，因此被拒。**管道名、引擎存活、代理都不是原因**。

**已排除项**（均已实测）：`DOCKER_API_VERSION` 环境变量不被 docker-java 采纳（字节码扫描 `DefaultDockerClientConfig` 只有 `API_VERSION` / `api.version` 两个键）；`~/.docker/config.json` 无代理、`NO_PROXY` 已设、无 `HTTP(S)_PROXY`。

**修复**：在 `server/pom.xml` 的 `maven-failsafe-plugin` 中固定系统属性：

```xml
<configuration>
  <systemPropertyVariables>
    <api.version>1.44</api.version>
  </systemPropertyVariables>
</configuration>
```

选 `1.44` 的理由：Docker Engine 25+ 均支持，且高于本机引擎实测下限；不依赖机器路径、环境变量或工作区外文件，任何机器上 `mvn verify` 都可复现。**注意**：若本机/CI 引擎更老、其支持的最高 API 版本低于 1.44，需按该引擎调小该值；排查同类问题的正确判据是"引擎支持的最低 API 版本"，不是"管道能否连上"。

**未采用的方案**：① 升级 Testcontainers 版本（当前由 Spring Boot 管理的版本同样支持 `api.version` 键，升级属不必要的连带改动）；② `disabledWithoutDocker = true` 静默跳过集成测试（会让本机基线实际没跑，属"假绿"）；③ 写 `~/.testcontainers.properties`（工作区外写入，换机器不可复现）。
